Part 17: Git and GitHub

This portion of the lab required more troubleshooting than originally anticipated because I had not completed all of the recommended Git and GitHub preparation in advance. As a result, I encountered several issues involving project organization, relative file paths, repository initialization, file staging, and GitHub authentication. These challenges ultimately provided a practical demonstration of why establishing the project structure and version-control environment early is an important part of a reproducible workflow.

The project was initially associated with an incorrect project location, which caused here() to reference the wrong directory. After correcting the project location and relative paths, the R environment was restarted, required packages and objects were reloaded, the code was rerun, and the Quarto document was rendered again. Rendering also helped identify and correct issues such as duplicate chunk labels and a syntax error that may otherwise have remained unnoticed.

Git was then initialized for the correct project directory. Because the directory contained files unrelated to this lab, I reviewed the untracked files and selectively staged only the five files associated with Lab 1. These were committed to the main branch using the message Complete Lab 1 reproducible workflow.

Finally, I created and connected the local repository to a GitHub repository. Initial attempts to authenticate through HTTPS using a personal access token were unsuccessful, so I configured SSH authentication instead. An ED25519 SSH key was generated locally, added to GitHub, and the repository remote was changed from HTTPS to SSH. The project was then successfully pushed to GitHub and verified online.

Overall, this process reinforced that reproducibility involves more than writing code that runs. It also depends on consistent project organization, relative file paths, a clean computing environment, intentional version control, and properly configured tools for sharing the work. Completing the recommended setup earlier would have prevented several of these complications, but troubleshooting them helped me better understand how each component of the workflow functions together.

Reflection Questions

Question 1

Why is reproducibility important in public health research and practice?

Research findings and data may be used to inform programs, policies, and decisions that affect entire populations. A reproducible workflow allows others to understand how results were produced, verify the process, and repeat the analysis when necessary. It also helps ensure that the work can still be understood and recreated even after time has passed or the project has been transferred to someone else.

Question 2

How does a consistent project structure improve collaboration and review?

Consistent project structure makes it easier for collaborators and reviewers to understand where data, figures, scripts, tables, and other materials are stored without having to search through an entire project. It also creates a shared organizational system, which reduces confusion when multiple people are working with the same files. This lab showed me that organization is not just about preference; the location and structure of files can directly affect whether code runs correctly.

Question 3

Why are relative paths preferable to absolute paths?

They reference files based on their location within the project rather than a location that is specific to one person’s computer. An absolute path may work on my computer but fail when another person opens the project because their username, folders, or file locations are different. Using relative paths makes the project more portable and allows the same code to work across different computers as long as the project structure remains consistent.

Question 4

How does GitHub contribute to reproducibility?

GitHub contributes to reproducibility by providing a central location where project files and changes can be stored and tracked over time. Git commits create a history of the work, which makes it possible to see what changed and when instead of relying on multiple disconnected versions of the same file. GitHub also allows collaborators or reviewers to access the same materials used to produce an analysis, which supports transparency and makes the work easier to reproduce.

Question 5

What was the most challenging part of the lab?

The most challenging part of the lab was configuring the project and Git/GitHub workflow, particularly because I had not completed all of the recommended setup in advance. I encountered issues involving the project location, relative paths, an empty R environment after restarting, selective file staging, and GitHub authentication. Although troubleshooting these issues took additional time, it helped me understand why the setup steps matter and how the different parts of a reproducible workflow depend on one another. By the end of the lab, I was able to rerun the analysis from a clean environment, render the document successfully, selectively commit the required files, and push the completed project to GitHub using SSH authentication.
